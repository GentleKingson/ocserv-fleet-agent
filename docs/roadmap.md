# Forward Roadmap

This roadmap starts from the current source tree and keeps `ocfleet` inside the
read-only ocserv fleet observability/control-plane boundary. It is an
implementation guide, not a production-complete claim.

| Phase | Goal | Deliverables | Safety boundary | Acceptance criteria |
| --- | --- | --- | --- | --- |
| Phase 0: Documentation/status baseline | Make project maturity and feature state unambiguous. | Updated README, `docs/status.md`, Phase 12 status notes, and doc claim checks in CI. | No new dangerous RPCs, providers, or ocserv mutations. | README states Phase 10/11 implemented, Phase 12 CLI observability partial, Web/API experimental read-only, and not production-complete; doc claim check passes. |
| Phase 1: CLI observability stabilization | Stabilize the active Phase 12 CLI surfaces around current args and deterministic output. | Scheduler, health, alert, retention, and audit export docs aligned with `ocfleet --help`; focused regression tests for output, redaction, and rejected paths. | CLI remains controller-local; scheduler uses fixed job kinds and does not infer trust or path-probe authorization. | Documented commands match `crates/ocfleet-cli/src/args.rs`; JSON outputs remain low-sensitive and deterministic. |
| Phase 2: Retention/audit hardening | Make local history pruning and audit export easier to operate safely. | Operator guidance for retention scopes, export windows, redaction modes, private output files, and checksum sidecars. | Retention never deletes controller audit, node registry, enrollment, endpoint trust, or scheduler configuration. | Dry-run and apply behavior are documented and tested; all local SQLite state mutations write controller audit. |
| Phase 3: Health/alert policy maturation | Refine advisory health and alert lifecycle behavior without adding remediation. | Clear policy docs, alert reason catalog, silence/resolve guidance, and JSONL delivery examples. | Alerts are notifications only; webhook remains disabled until separately designed; no shell, script, command, or automatic remediation hook. | Alerts contain bounded low-sensitive summaries only; webhook and forbidden hook types are rejected and tested. |
| Phase 4: Read-only API spec | Keep the HTTP API contract small and auditable as the implementation evolves. | API route contract, response DTOs, auth model, redaction rules, read-only SQLite access plan, and threat model. | API must not trigger agent RPCs, mutate trust, mutate scheduler jobs, run commands, read arbitrary files, or expose raw audit/RPC bodies. | Spec is reviewed against the global safety invariants; all routes are read-only and map to existing low-sensitive controller data. |
| Phase 5: Read-only API implementation | Harden the experimental API as a thin observation surface. | API crate/binary, read-only routes, bounded pagination, redacted responses, read-only startup behavior, and tests. | API uses explicit auth for non-loopback listeners and SQLite read-only data access; no RPC trigger endpoints and no local command or file selectors. | API tests prove no mutating routes, no RPC trigger route, no raw sensitive fields, and no unbounded response bodies. |
| Phase 6: Web dashboard | Mature the Web view on top of the read-only API. | Dashboard for fleet health, nodes, observations, runs, alerts, and audit export visibility. | Dashboard is an observation surface only; it must not create trust, run scheduler jobs, call agents, or perform ocserv management. | UI reflects API state accurately, has no control actions, and passes redaction and no-overlap visual checks. |
| Phase 7: Release readiness | Prepare a conservative release candidate without overstating maturity. | Install/upgrade docs, release notes, smoke tests, known limitations, and operational runbooks. | Release notes preserve read-only scope and explicitly exclude production-complete management claims. | Standard Rust checks, install smoke, doc claim checks, and security regression tests pass; docs list remaining work clearly. |
